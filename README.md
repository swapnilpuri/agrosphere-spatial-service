# AgroSphere Spatial Service

Milestone 1B, service 0.2.1. Independent Java 21 / Spring Boot 4.0.9 / Maven 3.9.12 project. Geometry and twin metadata live exclusively in the Spatial Service database. Estate identity and plantation business attributes remain owned by Estate Service. Contracts are pinned to the proposed contracts 0.3.0 release, including unchanged estate/block v2 snapshots from 0.2.0. No sibling source dependency exists.

## Build and verify

Use JDK 21 and Docker Desktop with Linux containers. JUnit Jupiter remains 5.14.4; tests manage Spring contexts directly because Spring 7 SpringExtension requires JUnit 6.

~~~powershell
.\mvnw.cmd verify
.\mvnw.cmd verify -Pintegration
python -m pip install -r requirements-test.txt
python scripts/validate_contracts.py
docker build -t agrosphere-spatial-service:0.2.1 .
python scripts/smoke_image.py
~~~

Use ./mvnw on Linux/macOS. The first command runs 19 unit/security tests. The integration profile additionally runs 12 real PostGIS/RabbitMQ/HTTP tests, using a local RSA-signed OIDC issuer; it does not require Estate Service or a deployed Keycloak. Docker/image-download failures fail the suite rather than silently skipping it. The contract script requires actual responses/envelopes generated by integration tests. Docker build also executes unit tests on Java 21. See [the completion report](docs/MILESTONE_1B_REPORT.md) for actual checks and discrepancies.

## Local startup and infrastructure

The existing infrastructure provisions agrosphere_spatial, owned by the non-superuser agrosphere_spatial role, and PostGIS. Flyway preserves V1 and creates V2 tables; the service fails explicitly if PostGIS has not been provisioned. Never delete existing volumes to apply migrations. Do not use the infrastructure administrator as the application role.

From agrosphere-infrastructure, configure its private .env as documented there, then:

~~~powershell
docker compose --profile identity up -d postgres rabbitmq keycloak
~~~

Provision the agrosphere realm, a spatial-service audience, trusted realm roles PLATFORM_ADMIN, ESTATE_ADMIN, ESTATE_MANAGER, AGRONOMIST and VIEWER, and an administrator-managed multivalued estate_ids JWT claim. Configure audience and estate scope through trusted identity administration, never user-editable attributes. .env.example contains placeholders only; Spring does not automatically load .env.

For host execution, export DB_URL, DB_USER, DB_PASSWORD, RABBITMQ_HOST, RABBITMQ_USER, RABBITMQ_PASSWORD and OIDC_ISSUER_URI using the example. Then:

~~~powershell
$env:DB_URL = 'jdbc:postgresql://localhost:5432/agrosphere_spatial'
$env:DB_USER = 'agrosphere_spatial'
$env:RABBITMQ_HOST = 'localhost'
$env:RABBITMQ_USER = 'agrosphere'
$env:OIDC_ISSUER_URI = 'http://localhost:8180/realms/agrosphere'
$env:OIDC_AUDIENCE = 'spatial-service'
# Set DB_PASSWORD and RABBITMQ_PASSWORD privately to match infrastructure.
$env:ESTATE_CONSUMER_ENABLED = 'true'
$env:OUTBOX_PUBLICATION_ENABLED = 'true'
.\mvnw.cmd spring-boot:run
~~~

Or run from agrosphere-infrastructure using the service-owned overlay:

~~~powershell
# Set OIDC_ISSUER_URI to the exact issuer reachable from the service container.
docker compose -f compose.yaml -f ../agrosphere-spatial-service/deploy/compose.spatial.yaml up -d --build postgres rabbitmq spatial
~~~

Provision identity first. Configure Keycloak's advertised hostname so the JWT issuer exactly matches OIDC_ISSUER_URI from both the client and service. localhost inside a container refers to that container; use suitable service DNS or host.docker.internal on Docker Desktop. The overlay reuses the infrastructure database/broker and does not modify its files or expose additional external ports. Keycloak start-dev remains local development infrastructure.

Standalone image command (supply a private .env containing container-reachable addresses):

~~~powershell
docker run --rm --env-file .env -p 127.0.0.1:8082:8082 agrosphere-spatial-service:0.2.1
~~~

Only /actuator/health and its probe subpaths are public. /actuator/health/readiness includes database connectivity; /actuator/health/liveness checks process availability. Business APIs, /v3/api-docs and /swagger-ui/index.html require a bearer JWT. Import the pinned OpenAPI into an authenticated API client or use an authenticated local proxy for Swagger UI. The runtime OpenAPI uses the same pinned typed schemas as the contract repository. Structured JSON logs include correlation IDs; geometry modifications also log actor, feature ID and revision.

## REST and GeoJSON

All operations begin /api/v1/spatial. [Pinned OpenAPI](src/main/resources/contracts/spatial-service.openapi.json) lists every field, response and error. Features: POST /features, GET/PUT /features/{id}; estate collections: GET /estates/{estateId}/features and /boundaries; blocks: GET /blocks/{blockId}/geometry and /history. Queries: POST /query/point, /query/intersects, /query/within and GET /estates/{estateId}/bbox. Layers: POST /layers, GET/PUT /layers/{id}, GET /estates/{estateId}/layers. Assets: POST /assets, GET /assets/{id}, GET /estates/{estateId}/assets. Import/export: POST /imports/geojson, GET /imports/{jobId}, GET /estates/{estateId}/export/geojson. POST /transform explicitly converts a point from EPSG:3857 or EPSG:4326 into canonical WGS84.

Collection page is zero based (0–100000); size is 1–100. Export defaults to 100, other collections to 20. Stable UUID ordering. GeoJSON export is a paged FeatureCollection with page/size/totalElements extension members; fetch every page for a complete estate. Block history retains all versions, capped at 1000 inline records; larger histories require a reviewed database export and return 422. No history is silently truncated. Query responses expose truncated when the result exceeds limit; narrow the bbox to retrieve more.

Feature input includes estateId, referenceEntityId, referenceEntityType, featureCode, geometry, srid=4326, status, sourceType and explicit dataProvenance. PUT additionally requires current geometryVersion. IDs, creation timestamps, estate ownership and canonical entity references are immutable. Codes contain 1–64 uppercase letters/digits/underscore/hyphen. Polygon, MultiPolygon, Point and LineString are supported; polygonal features appear in /boundaries. One active authoritative feature per entity is enforced in the database. Metadata-only updates also create a new feature revision. Layer PUT requires current version. There are no delete endpoints.

Coordinates are finite two-dimensional [longitude, latitude]. Legacy crs objects, invalid rings/holes/self-intersections, empty/degenerate geometry, out-of-range coordinates and antimeridian-spanning envelopes are rejected with actionable errors. No automatic repair is performed. Import boundaries must already be EPSG:4326; projected GeoJSON is never silently relabeled. POST /transform is explicitly limited to 2D points in 4326/3857, not general datum conversion or surveying.

Area uses PostGIS ST_Area(geometry::geography)/10000, with spheroidal square metres converted to hectares. Non-area geometries return null hectares. MINIMUM_AREA_HECTARES and OVERLAP_TOLERANCE_HECTARES are configurable (both default 0, while degenerate polygons are always invalid). Active block polygons may share edges but cannot overlap above tolerance. Existing estate/division polygon boundaries cover new child geometries; parent edits must continue to cover existing children. Missing parent geometry does not prevent initial creation, but a later parent boundary is checked against existing children. All geometry writes in an estate serialize while applying these rules, and conditional revision updates reject lost writes.

Query bodies require estateId, geometry, bbox=[west,south,east,north] and optional limit=1–100. Geometry must lie within bbox; each bbox dimension is limited to MAX_QUERY_BBOX_DEGREES (default 5). Point uses ST_Covers, so shared-boundary points can return adjacent features. Intersects uses ST_Intersects; within returns stored features covered by the supplied polygon. GiST bounding-box prefilters bound searches. MAX_COORDINATES defaults to 20000; MAX_BODY_BYTES defaults to 2097152 and bounds streamed JSON bodies as well as Content-Length requests.

Import accepts JSON {estateId, sourceFilename, geojson: FeatureCollection}, not multipart files. Filename is a simple .geojson basename. Include featureCode, referenceEntityId, referenceEntityType, status and dataProvenance in properties. Import sets sourceType=IMPORT, sourceReference=filename and srid=4326. At most 100 features are processed atomically in the calling request. It returns 202 with a durable COMPLETED or FAILED job; failures retain an actionable report, import zero features and publish no partial events. Top-level malformed uploads return 400. CSV is reserved in the job model and has no endpoint in this milestone. No filesystem path is accepted or opened.

Assets use HTTPS metadata URIs only, with no credentials/fragments. The service does not fetch remote resources. Position is an optional WGS84 Point. Orientation x/y/z represents roll/pitch/heading in degrees; scale x/y/z is a positive dimensionless factor. Asset-feature relationships must belong to the same estate. TREE_MODEL requires SIMULATED provenance and is illustrative, never an assertion of surveyed individual-tree position. 3D Tiles is supported as layer format=3D_TILES plus sourceUri metadata; no terrain, renderer or client is implemented.

## Security and errors

Nimbus verifies signed RS256 JWT issuer, audience and lifetime. PLATFORM_ADMIN accesses every estate. ESTATE_ADMIN and ESTATE_MANAGER write assigned estates; those roles plus AGRONOMIST and VIEWER read assigned estates. AGRONOMIST is read-only in this milestone. Import requires the write role and estate scope. Requests resolve persisted ownership before resource access; client estate IDs never confer permission. All list/query/export requests are scoped before data is retrieved.

Errors use RFC 9457 application/problem+json with correlationId. Missing/invalid authentication returns 401, scope/write denial 403, invalid input 400, missing resource 404, duplicate assignment/code or stale revision 409, oversized body 413. UUID X-Correlation-ID is returned; malformed/missing values are replaced. Responses do not expose stack traces or filesystem paths. Server-side logs are operational evidence and must be access controlled.

## Events, references and recovery

ESTATE_CONSUMER_ENABLED defaults false so independent startup needs no Estate Service or broker connection. Enable it to declare durable spatial.estate.v2, bound to agrosphere.EstateCreated.v2, EstateUpdated.v2, PlantationBlockCreated.v2 and PlantationBlockUpdated.v2 on agrosphere.domain. Messages are checked against pinned full v2 JSON Schemas, including formats and envelope/payload identity agreement. Contract fixtures can seed the projection without Estate Service. A missing active estate/entity projection rejects writes with 400; reads never call Estate Service synchronously.

Only canonical IDs, estate/parent IDs, lifecycle status and snapshot revision are retained. M1A emits no division events, so division membership is inferred from validated block snapshots and explicitly marked inferred; independent division lifecycle cannot be established yet. Estate/block lifecycle is authoritative; revisions handle update-before-create and stale delivery. An estate or block inactivation blocks future writes but does not erase spatial history. Membership/lifecycle changes can require operator reconciliation of existing geometry.

Projection and processed_event insertion commit together; listener AUTO ACK occurs after successful transactional return. Retry is bounded to three attempts with exponential backoff, then broker dead-letters to spatial.estate.v2.dead through spatial.dead. No infinite requeue. Review and repair the cause before republishing a retained envelope to its original routing key; preserve eventId and correlationId. Invalid messages have no committed idempotency marker. Broker/DLQ retention, alerting and operator permissions remain deployment responsibilities.

The domain mutation and spatial outbox insert use the same database transaction. Events: SpatialFeatureCreated, SpatialFeatureUpdated, SpatialBoundaryChanged, SpatialLayerCreated and DigitalTwinAssetRegistered. Spatial events use eventVersion=1 and routing agrosphere.<EventType>.v1; their schemas live under events/spatial/v1, distinct from unchanged foundation events/v1. Feature events include referenceEntityId and geometryVersion; payloads contain IDs/provenance/status rather than large geometries. Retrieve authoritative geometry by feature ID/version history.

OUTBOX_PUBLICATION_ENABLED defaults false; enable after consumers bind queues. The relay uses persistent mandatory publishing, correlated confirms, SKIP LOCKED batches and retained FAILED rows after bounded retries. Defaults: 20/batch, 1 second polling, 5 second confirm timeout, 10 attempts, exponential retry from 5 seconds capped at one hour. OUTBOX_BATCH_SIZE, OUTBOX_POLL_MS, OUTBOX_CONFIRM_TIMEOUT_SECONDS, OUTBOX_MAX_ATTEMPTS and OUTBOX_RETRY_SECONDS configure this. At-least-once delivery can repeat eventId after a confirm/commit crash; downstream consumers must deduplicate. Database transaction timeouts must exceed worst-case batch confirm time. After fixing delivery and reviewing a specific row, an authorized database operator can replay it:

~~~sql
UPDATE outbox_event SET delivery_status='PENDING', attempts=0, next_attempt_at=now()
WHERE event_id='<reviewed-event-uuid>' AND delivery_status='FAILED';
~~~

No automatic outbox/history/idempotency purge is implemented. Define retention after reconciliation/replay requirements are agreed. See [synthetic fixture instructions](examples/README.md). No Estate Service internals, cloud resources, remote repositories, pushes, client applications or Milestone 1C functionality are changed.
